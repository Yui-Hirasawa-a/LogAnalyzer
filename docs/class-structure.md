# Каркас Server Log Analyzer

Це перший етап проєкту на C++20: класи, перелічення та оголошення методів.
Читання журналу, розбір рядків, підрахунок статистики, меню та запис звіту
ще не реалізовані. Основою є UC-01, UC-02 та UC-03 з `docs/user-cases/`.

## Структура файлів

```text
src/
  main.cpp
  domain/
    HttpMethod.hpp
    LogEntry.hpp
    LogFile.hpp
    LogStatistics.hpp
  application/
    AnalysisState.hpp
    LogAnalyzer.hpp
  infrastructure/
    LogParser.hpp
    ReportWriter.hpp
  presentation/
    MenuAction.hpp
    ConsoleApp.hpp
```

`domain` містить дані предметної області, `application` керує активним журналом
та аналізом, `infrastructure` працюватиме з файлами, `presentation` — з консоллю.
Це просте розділення відповідальностей без базових класів, фабрик і зайвого успадкування.

## Які класи є і для чого

| Клас | Що зберігає / за що відповідає |
| --- | --- |
| `LogEntry` | Один коректний запис: IP, identity, користувач, час із часовим поясом, HTTP-метод, адреса запиту, протокол, числовий код відповіді, розмір тіла відповіді, referer та user-agent. |
| `LogFile` | Шлях до завантаженого журналу, колекція коректних записів та кількість пропущених рядків. Не тримає файл відкритим. |
| `LogStatistics` | Загальна кількість запитів, кількість відповідей 4xx, кількість відповідей 5xx та кількість унікальних IP. |
| `LogParser` | У майбутньому читатиме Combined-файл через `load()`. Приватний `parseLine()` розбиратиме один рядок. |
| `LogAnalyzer` | Володіє активним журналом і результатами його аналізу. Має `openLog()` та `analyze()`. |
| `ReportWriter` | Зберігатиме дані журналу й статистику в унікальний `.txt` у вибраній папці та повертатиме повний шлях. |
| `ConsoleApp` | Показуватиме меню, прийматиме вибір і викликатиме потрібні операції. Володіє аналізатором та об'єктом запису звіту. |

Час поки зберігається рядком: юзкейси не вимагають фільтрації чи обчислень за датами.
HTTP-код зберігається числом, щоб пізніше рахувати діапазони 400–499 і 500–599.
Не потрібно створювати enum для кожного можливого коду.

## Enum class

- `HttpMethod`: `Get`, `Post`, `Put`, `Delete`, `Patch`, `Head`, `Options`,
  `Connect`, `Trace`, `Other`. `Other` залишає місце для інших HTTP-методів.
- `AnalysisState`: `Empty`, `LogLoaded`, `Analyzed` — журнал ще не відкритий,
  журнал завантажений, аналіз завершений.
- `MenuAction`: `Exit = 0`, `OpenLog = 1`, `AnalyzeLog = 2`, `SaveReport = 3`.
  Під час реалізації введене число потрібно перевірити до перетворення на цей тип.

`enum class` створює окремий тип. Наприклад, пункт меню записується як
`MenuAction::OpenLog`, а не як незрозуміле число `1` у коді обробки вибору.

## Інкапсуляція простими словами

Усі поля класів приховані в `private`. Інший код не зможе напряму змінити
кількість помилок, підмінити записи або випадково залишити стару статистику.

У класів даних є конструктори для передачі початкових значень і публічні
геттери для читання. Сеттерів для кожного поля немає: запис і статистика
мають створюватися як цілісні об'єкти. Перевірки значень у конструкторах
ще не написані — вони належать до наступного етапу реалізації.

`const std::string&` або `const std::vector<LogEntry>&` означає повернення
посилання для читання без копіювання всього рядка чи колекції.
`const` після методу, наприклад `getStatusCode() const`, означає, що цей
метод не змінює об'єкт. Посилання дійсне, доки існує відповідний об'єкт;
посилання на старі записи не слід зберігати після заміни активного журналу.

Символ `_` у кінці назви, наприклад `entries_`, просто відрізняє поле
від параметра конструктора. `#pragma once` захищає заголовок від повторного
підключення в межах одного файлу компіляції.

`std::size_t` використовується для кількостей. `std::uint64_t` — для розміру
відповіді в байтах. `std::filesystem::path` — для шляхів до файлів та папок.

## Навіщо optional

`std::optional<T>` означає «значення типу T або його відсутність».

- `activeLog_` відсутній, поки журнал не завантажено.
- `statistics_` відсутня, поки аналіз не виконано. Це відрізняється від
  готової статистики, у якій деякі лічильники дорівнюють нулю.
- `parseLine()` зможе повернути `std::nullopt` для некоректного рядка.
- `responseBytes_` зможе бути відсутнім, якщо у журналі розмір задано як `-`;
  нуль байтів і невідомий розмір — різні значення.

Окремого поля зі станом у `LogAnalyzer` немає. `getState()` має визначати
стан за наявністю журналу й статистики, щоб ці дані не суперечили одне одному.

## Як це відповідає юзкейсам

### UC-01: відкрити журнал

Майбутній виклик: `ConsoleApp::openLog()` → `LogAnalyzer::openLog(path)` →
`LogParser::load(path)` → приватний `parseLine(line)` для кожного рядка.
Результат — `LogFile`, де кількість завантажених рядків береться з розміру
`entries_`, а пропущених зберігається окремо.

Під час реалізації недоступний, порожній файл або файл без коректних записів
має спричиняти зрозумілу помилку. Для таких збоїв достатньо стандартних винятків
із повідомленням; консоль їх перехоплюватиме. Некоректний окремий рядок має
пропускатися, а не переривати завантаження всього файлу.

Новий журнал потрібно спочатку повністю завантажити в тимчасовий об'єкт.
Лише після успіху замінити активний журнал і скинути попередню статистику.
Невдала спроба відкриття має залишити попередні дані доступними.

### UC-02: проаналізувати журнал

`ConsoleApp::analyzeLog()` викличе `LogAnalyzer::analyze()`.
Аналізатор перевірятиме наявність журналу й створюватиме `LogStatistics`
за його записами. Консоль читатиме результат через геттери.
Внутрішній набір унікальних IP знадобиться під час реалізації, але зберігати
його окремим полем заради готового лічильника зараз не потрібно.

### UC-03: зберегти звіт

`ConsoleApp::saveReport()` перевірятиме, чи завершений аналіз, запитуватиме
папку й передаватиме активний `LogFile` та його `LogStatistics` у
`ReportWriter::save()`. Саме цей клас створюватиме унікальну назву `.txt`.
Із журналу він візьме назву файлу та кількість пропущених рядків.
Помилка запису не повинна скидати результати: користувач зможе вибрати іншу папку.

## Що працює зараз

Є структура типів і налаштування збирання на C++20. `main()` підключає
заголовки й одразу завершується з кодом `0`; меню поки не запускається.

Конструктори, геттери та робочі методи лише оголошені, без тіл.
Ініціалізатори полів задають початкові значення, але не реалізують логіку.
Якщо зараз почати викликати оголошені методи або конструктори даних,
компонувальник повідомить про відсутню реалізацію. Це очікувано для цього етапу.
Пізніше реалізації додаватимуться у відповідні `.cpp`, а файли — до CMake.

Команди з кореня проєкту:

```powershell
cmake -S . -B build -G "MinGW Makefiles"
cmake --build build
.\build\LogAnalyzer.exe
```

Цей приклад розрахований на встановлені CMake та MinGW. Для іншого компілятора
потрібно вибрати відповідний генератор CMake.

## Наступний етап

1. Реалізувати конструктори та геттери класів даних.
2. Реалізувати завантаження й розбір Combined, включно з пошкодженими рядками.
3. Реалізувати зміну активного журналу, скидання старої статистики й аналіз.
4. Реалізувати запис звіту та обробку помилок збереження.
5. Реалізувати меню й викликати `ConsoleApp::run()` із `main()`.

На цьому етапі ці функції навмисно не реалізовані.
